Comprehensive Revision Notes: TicTacToe Game Development
Overview
This class explored the design and implementation of a TicTacToe game, focusing on key areas such as developing winning strategies, implementing an undo feature, creating a class diagram, and applying design patterns. We started with understanding the problem framework, moved through optimizing the game logic and concluded with the structural setup for the game code.

Understanding the Game Framework
Overview and Alignment
Overview Stage: Establishing a shared understanding of the problem with the interviewer is critical to ensure alignment and avoid confusion. It includes clarifying:
System interactions: CLI, GUI, or entity-based.
Data persistence requirements.
Game Requirements
Grid: Dynamic or constant, typically n x n.
Players:
Each player has a unique symbol decided at game start.
Possibility of bot players with varying difficulties.
Game Flow:
Random selection for which player starts.
User-defined winning strategies: row-wise, column-wise, or diagonal-wise.
Additional considerations: tournament settings, leaderboards, and time per move were mentioned but not implemented.
Developing Winning Strategies
Basic Concept
Determine the game outcome by checking if a player has a complete row, column, or diagonal.
Draw Condition: Occurs when the grid has no further moves.
Initial Approach
Brute Force: Check each row, column, and diagonal after every move for a win:
Iterate over all players and all grid lines to see if any line is fully filled by a player's symbol.
Time Complexity: O(n³), not efficient.
Optimized Approaches
Optimize Checks:
Only check the player who made the last move if they won.
Only check the specific row, column, and diagonals linked to the last move's position.
Running Count Approach:
Maintain counts of player symbols in each row, column, and diagonals.
Adjust counts with each move and check these counts for a win.
Perform these checks in O(1) time complexity by using state arrays.
Implementing Undo Functionality
Concepts
Stack-Based Approach: Maintain a stack of moves to facilitate undoing a move.
State Tracking: Record the board's state after each move, allowing restoration when undo is requested.
Features of Undo
Restore the previous state upon undo request.
Update the board and player turn accordingly.
Class Diagram and Design Patterns
Class Components
Game Core:
Board: Holds grid details.
Players: Human and Bot, differentiated by strategy patterns.
Moves: Knowledge of move history.
Mechanics:
Winning Strategies stored as strategies.
Game State enum: To manage the game's current status.
Design Patterns Used
Strategy Pattern: Used for implementing the flexible winning conditions and bot playing levels.
Builder Pattern: To construct and validate the game setup.
Factory Pattern: To create player instances based on type (Human/Bot).
Example: Winning Strategy Optimization
Example Scenario
Suppose a player moves to (2, 2) on a 3x3 grid:
Check row 2, column 2, and both diagonals for a win.
Update the corresponding counters, allowing for an O(1) check for complete lines.
Analogies
Treat the game as a series of DSA problems, optimizing both time and space complexity by balancing between in-memory calculations and pre-stored states.
Conclusion
This session provided a deep dive into structuring a TicTacToe game efficiently through strategic use of algorithms and design patterns. The emphasis was on reducing complexity from O(n³) to O(1) for critical operations like determining a winner, alongside implementing user-friendly features like undo. Applying strategy and builder patterns allows flexibility and scalability, ensuring that the game design is adaptable to different configurations and expansions.

Comprehensive Revision Notes: Low-Level Design (LLD) Foundations
Overview
This class focused on the fundamental components of Low-Level Design (LLD) in software engineering, emphasizing the importance of structuring code through distinct sections such as models, controllers, and data transfer objects (DTOs). We discussed practical examples and analogies to solidify the concepts of organizing and structuring software projects, particularly in the context of object-oriented design.

Models
Models represent the core entities within a system we design. They encapsulate the data attributes and behaviors relevant to these entities.

Models: Represent entities in the system. Each entity identified results in a class creation.
Class Diagrams: Help identify the entities and their relationships, which become classes in the code.
Steps to Define Models
Identify Entities: Use class diagrams to determine entities.
Create Classes: Each entity becomes a class with attributes and methods.
Attributes: Include necessary fields (e.g., ID, name) as part of your class design.
Inheritance in Schema:
Use parent tables for common attributes and child tables for specific ones to avoid redundancy.
Example: Pen Class Inheritance
Pen (Parent)
   ├── BallPen (Child)
   └── GelPen (Child)
Pen: Has common attributes such as brand, name, price.
BallPen and GelPen: Contain specific attributes (e.g., ink type for GelPen).
Controllers
Controllers act as intermediaries between models and views, handling input, processing requests, and returning responses.

Purpose: They are the entry points of the application, handling requests.
Analogy: A controller is like a hotel reception desk; it facilitates communication without performing the core tasks.
Responsibilities
Receive Requests: Handle incoming requests.
Delegate Work: Pass tasks to models or services for processing.
Return Responses: Collect data from models/services and send back a response.
Example Code Snippet
class TicketController:
    def issue_ticket(self, request: IssueTicketRequestDTO) -> IssueTicketResponseDTO:
        ...
        return response_dto
Data Transfer Objects (DTOs)
DTOs are simple objects used to transfer data between processes or layers in an application.

Request DTOs: Encapsulate data coming from the client.
Response DTOs: Encapsulate data sent back to the client.
Purpose: Ensure only necessary information is shared outside the service.
Benefits
Decoupling: Keeps controllers simple and decouples request/response from actual code logic.
Security: Limits the exposure of internal attributes.
Analogies
Controller Analogy
Controllers as Reception Desks:

Function: Controllers are like reception desks at a hotel. They manage requests (e.g., booking a room) but do not perform the actual task (e.g., cleaning a room or cooking food). This analogy emphasizes their role in processing requests and delegating to the appropriate service, much like a receptionist delegates tasks to hotel staff.
Example: Handling Inheritance
We covered inheritance in database schemas to optimize querying, ensuring common attributes reside in parent tables to prevent redundancy and complex queries involving unions.

Conclusion
Understanding the structuring of code using models, controllers, and DTOs is crucial for building maintainable and scalable software systems. These concepts help streamline processing, clarify responsibilities, and protect the integrity of data exchanges across different layers within an application. Mastery of these components will support efficient system designs, improve code readability, and enable easier maintenance and updates in the long term.

Layered Architecture
Components
Controller: Acts as an interface between models and services, handling incoming requests and sending responses.
Service: Contains the core business logic, coordinating actions between controllers and repositories.
Repository: Responsible for data storage and retrieval, providing a persistence layer, often acting on databases.

DTOs (Data Transfer Objects): These are used to transfer data between software application subsystems. Two main types are:

Request DTOs: For client-to-service communication.
Response DTOs: For service-to-client communication.
Models: Define the data structure, often encapsulating database entities.

Key Responsibilities
Executes main business operations.
Isolates the logic from data access operations, enabling cleaner architecture and easier maintenance.
Coordinates with repositories to perform data retrieval and updates.

Example Code
def issue_ticket(self, gate_id: int, vehicle_number: str, vehicle_type: VehicleType, owner_name: str) -> Ticket:
    gate = self.gate_repository.find_by_id(gate_id)
    if gate is None or gate.gate_type != GateType.ENTRY:
        raise InvalidGateException("Cannot issue a ticket at an exit gate")

    vehicle = Vehicle(vehicle_number, vehicle_type, owner_name)
    assigned_spot = self.allotment_strategy.find_spot(
        self.parking_spot_repository.find_all(), vehicle_type
    )
    if assigned_spot is None:
        raise ParkingFullException("No available spot for this vehicle type")

    assigned_spot.parking_spot_status = ParkingSpotStatus.OCCUPIED
    self.parking_spot_repository.save(assigned_spot)

    ticket = Ticket(
        number=str(uuid.uuid4()),
        entry_time=datetime.now(),
        vehicle=vehicle,
        assigned_spot=assigned_spot,
        generated_at=gate,
        generated_by=None,
    )
    return self.ticket_repository.save(ticket)
Repository Layer
Purpose: Interface for data operations such as fetching, saving, and deleting records.
Design: Designed to be generic, allowing easy adaptation to various data models like Gate, Ticket, etc.

The Concurrency Issue
Problem: Simultaneous requests from different gates could potentially issue the same parking spot to multiple vehicles.
Solution: Use locking mechanisms to ensure that only one thread can process a spot assignment at a time.

    )

Comprehensive Revision Notes: Concurrency Problems in Ticket Booking Systems
Overview
This session focused on understanding the concurrency problems encountered when booking a ticket, specifically in systems like BookMyShow. These issues are crucial in interviews and real-world applications, particularly concerning race conditions and booking consistency. We explored the implications of using reserved keywords in databases, the specific challenges posed by race conditions, and strategies to mitigate them using locking mechanisms.

Database Reserved Keywords
Definition and Problem
Reserved Keywords: Words reserved by the database language for internal use, like SELECT, FROM, USER.
Using these as table names can cause conflicts and errors depending on the database used.
Solution
Use plural forms for table names (e.g., users, shows) to avoid using reserved words, ensuring compatibility across different databases.
This simple practice mitigates potential conflicts and maintains consistency in naming conventions.
Booking Flow and Race Conditions
Booking Process
Seat Selection: Users select seats, but at this point, no actual booking occurs.
Confirmation: A temporary hold is placed on seats during payment processing.
Payment: If completed within the hold period, the booking is confirmed.
Race Condition Problem
Check-Then-Act Race Condition: This occurs when two users simultaneously select the same seat. Both threads may see the seat as available and proceed to book it, leading to double booking.
Database Isolation Levels
Repeatable Read: Default in MySQL, allows reading consistency within a transaction but does not prevent race conditions.
Serializable: Enforces sequential transaction execution, preventing concurrent transactions from modifying the same data simultaneously, thus avoiding race conditions.
Solutions to Mitigate Race Conditions
Hard Locks and Their Pitfalls
Acquiring a database lock during booking could prevent double booking but holds resources for too long, impacting performance.
Soft Locks
Use a status field to represent locks (e.g., BLOCKED status) to indicate that a seat is temporarily held, without maintaining long database transactions.
Soft locks allow for shorter transaction windows, consuming fewer resources.
Hybrid Approach
Combine soft locks with a higher isolation level (SERIALIZABLE) to ensure that only one booking transaction can proceed when targeting the same seat, effectively using both soft and hard locking strategies where appropriate.
Why Python Locks Don't Suffice
Process-specific Locks: Thread locks in Python apply only to a single process and won't manage race conditions across multiple processes or distributed systems, which BookMyShow uses.
Conclusion
Today's class delved into how concurrency is managed in ticket booking systems through careful application of database locks and strategic use of system design to avoid race conditions. The takeaway is that understanding how to manage concurrent processes effectively is critical in ensuring data integrity and that proper system design prevents conflicts in multi-user environments. This knowledge has broad applicability in both interviews and software development.

Developing the Booking Service
Concurrency Handling
Problem: Concurrent booking attempts could result in the same seat being booked by multiple users.
Key Term: Check and Set Deadlock: Occurs when a check and update on data are non-atomic, leading to race conditions.
Solution:
Database Locks: Initially considered using database transactions from booking initiation through payment, but this was inefficient.
Python Locks: Disregarded due to limitations in distributed environments where applications run on multiple servers.
Hybrid Approach: Combined lightweight database locks with Python logic, using SERIALIZABLE isolation level for transactions to manage concurrency effectively.
Lazy Seat Expiry
Implemented a lazy approach to handle the expiry of blocked seats.
Logic:
Check if the seat status was blocked.
Determine if the block time exceeded the allowed period (e.g., 15 minutes).
If yes, free up the seat for new booking attempts.
Code Example
from datetime import datetime, timedelta

for show_seat in show_seats:
    is_available = (show_seat.show_seat_status == ShowSeatStatus.AVAILABLE)

    is_expired_block = (
        show_seat.show_seat_status == ShowSeatStatus.BLOCKED
        and datetime.now() - show_seat.blocked_at > timedelta(minutes=EXPIRY_MINUTES)
    )

    if not (is_available or is_expired_block):
        raise RuntimeError(f"Seat {show_seat.seat.num} is not available")
Implementing User Authentication
Password Hashing with bcrypt
Problem: Storing passwords in plaintext is insecure.

Solution: Use bcrypt to hash passwords with a random salt, ensuring that even identical passwords result in different hashes each time.

Key Terms:

Salt: A random string added to the password before hashing to ensure unique hash outputs.
encode() and matches(): Bcrypt functions to hash passwords and verify hashes against stored values.
Code Example
import bcrypt

class PasswordHasher:
    def encode(self, raw_password):
        raw_bytes = raw_password.encode("utf-8")
        hashed_bytes = bcrypt.hashpw(raw_bytes, bcrypt.gensalt())
        return hashed_bytes.decode("utf-8")

    def matches(self, raw_password, stored_hash):
        return bcrypt.checkpw(raw_password.encode("utf-8"), stored_hash.encode("utf-8"))
Automatic Timestamp Updates
Used SQLAlchemy's default=datetime.utcnow and onupdate=datetime.utcnow features to automatically manage timestamp fields like created_at and last_modified_at.

Commands via the Command Line
Command Pattern Overview
Problem: Naive command handling in main() violates Single Responsibility Principle (SRP).

Solution:

Implement a Command interface with methods to match and execute commands.
CommandExecutor iterates through commands, handling execution based on input.
class Command(ABC):
    @abstractmethod
    def matches(self, user_input): ...

    @abstractmethod
    def execute(self, user_input): ...

class CommandExecutor:
    def __init__(self, commands):
        self.commands = commands

    def execute(self, user_input):
        for command in self.commands:
            if command.matches(user_input):
                command.execute(user_input)
                return
        print("Invalid command")

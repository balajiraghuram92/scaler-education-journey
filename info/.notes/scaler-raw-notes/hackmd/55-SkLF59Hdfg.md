Section 2: Bug Fixing, Reserved Keywords
What It Means

A question worth asking directly: an entity called User exists. If the app runs against a real database, and Hibernate tries to create a table literally named user, could that fail, even though the Java code itself is completely fine?

The Java code is not the problem.
Every real database has its own set of reserved words, words the database itself uses for its own commands.
If a table name matches one of those reserved words, it can break outright, or need special handling to work at all.
PostgreSQL: "user" is reserved → breaks
MySQL:      "user" is fine, but "show" is reserved
Both:       "row" is reserved

This project's application.properties connects specifically to MySQL, so User is not actually a problem today, but Show is. Both get fixed anyway, since this system might not always run against MySQL specifically, and fixing both is simply good practice.
Practical Mechanics
@Getter
@Setter
@Entity(name = "users")
public class User extends BaseModel {
    ...
}

@Getter
@Setter
@Entity(name = "shows")
public class Show extends BaseModel {
    ...
}

@Entity(name = "...") sets the table's real name directly. By default, Hibernate simply uses the class name, and that breaks on MySQL for one of these two classes. Naming the table explicitly avoids the problem regardless of which database ends up being used.

A related question worth asking: Seat.rowVal and Seat.colVal were already named that way back in Post-Read 9, not row and col. Was that a lucky guess, or good instinct? At the time, it simply felt like a safer name to use. It turns out this choice was avoiding this exact reserved-keyword bug before the bug itself had even been named. Nothing needs fixing on Seat as a result.

Quiz Recap

Someone adds a new entity called Order, for corporate bulk bookings. ORDER is a reserved SQL keyword. How should this class be written?

A) @Entity public class Order extends BaseModel {...}, Hibernate will handle the conflict on its own
B) @Entity(name = "orders") public class Order extends BaseModel {...}
C) Rename the Java class itself to OrderEntity
D) @Table(name = "order") with backticks typed inside the string
Correct answer: B. This is the exact same fix already applied twice, to User and to Show.
Why A is wrong: Hibernate does not protect against reserved keyword conflicts automatically; leaving the class unnamed means the table gets created using the raw class name, which fails against the reserved word.
Why C is wrong: it confuses the Java class name, which was never the actual problem and is fine to leave as Order, with the table name, which is the real source of the conflict.
Why D is wrong: manually embedding backticks inside a @Table(name = ...) string is more complicated than necessary and database-specific (backtick escaping is a MySQL convention, not universal); renaming the table outright, exactly as already done twice, is simpler and more portable.
Hidden Pitfalls
Assuming Hibernate automatically escapes or protects against reserved keyword conflicts: it does not; a class name colliding with a reserved SQL keyword produces a real failure unless the table is explicitly renamed via @Entity(name = "...").
Fixing this only for the database currently being used: today's application only connects to MySQL, where User isn't actually a problem, but fixing only what breaks on the current database leaves a landmine for any future switch to a different database engine.
Section 3: The Booking Use Case, Controller and DTOs
What It Means

Today's central requirement is booking a seat, this is where R10 and R11 finally get solved for real.

Practical Mechanics: From Controller to RestController
@Controller
public class BookingController {
    public BookMovieResponseDto bookMovie(BookMovieRequestDto request) {
        // ...
    }
}

A question worth checking directly: @Controller in Spring MVC is meant for returning web pages, "render this HTML page." A JSON response is needed instead, for an API client. Does plain @Controller do that?

No. Spring would try to treat whatever gets returned as the name of a page to render, not as raw data. The fix is @RestController, which is simply @Controller plus @ResponseBody, meaning: always send the return value back as raw data (JSON), never as a page.

@RestController
@RequestMapping("/booking")
public class BookingController {

    @PostMapping("/book")
    public BookMovieResponseDto bookMovie(@RequestBody BookMovieRequestDto request) {
        // ...
    }
}

Practical Mechanics: The Request and Response DTOs

What should flow in and out of this method, and why IDs rather than full objects, is worth reasoning through directly:

Both the input and the output should be DTOs. Raw model objects never cross the controller boundary directly.
A full object might expose internal details that should stay hidden.
The client calling this endpoint might not even be written in Java, it could be a mobile app or an entirely different backend, so matching this system's exact internal object shape creates unnecessary coupling.
IDs are simple and work identically across any language. The server does the real lookup itself.
@Getter
@Setter
public class BookMovieRequestDto {
    private List<Long> showSeatIds;
    private Long userId;
    private Long showId;
}

Once a booking succeeds, the client needs to know whether it worked, how much it cost, and some kind of booking identifier:

public enum ResponseStatus {
    SUCCESS, FAILURE,
}

@Getter
@Setter
public class BookMovieResponseDto {
    private ResponseStatus responseStatus;
    private int amount;
    private Long bookingId;
}

Hidden Pitfalls
Using plain @Controller for a JSON API endpoint: Spring interprets the return value as a view name to render rather than raw response data, breaking any client expecting JSON.
Accepting or returning full model objects directly through a Controller: this exposes internal object structure to external clients and creates unnecessary coupling between this system's internal shape and every consumer of the API; DTOs built from IDs avoid both problems.
Section 4: The Booking Flow and the Race Condition, as One Story
What It Means

Before writing the service, it's worth understanding where R10 and R11 actually come from, as one connected story.

Almost every ordering flow, food delivery, online shopping, ticket booking, follows the same three steps: selection → confirmation → payment.

[ Selection ] -> [ Confirmation ] -> [ Payment ]

A question worth asking directly: why does a confirmation step exist at all? Why not go straight from selecting to paying?

Part of the answer is that it's a final summary before committing, but there's a bigger reason:

In the selection step, nothing has actually been booked yet, only selected.
Someone else could be looking at the exact same seats at the exact same moment.
If both people go straight to payment with no protection in between, a collision happens.

The moment someone clicks "book," the seats are not handed over permanently. A temporary hold gets placed on them instead, usually around 15 minutes. If payment isn't completed within that window, the hold expires and the seats become available again. This is R10 in action, and it's visible on most real ticketing sites as a literal countdown timer once seats are picked.

Stating the actual problem plainly:

Two users, A and B, both try to book the SAME ShowSeat,
for the SAME Show, within milliseconds of each other.

Practical Mechanics: The Naive Version, and Where It Breaks
public Booking bookMovie(Long userId, List<Long> seatIds, Long showId) {
    User user = userRepository.findById(userId).orElseThrow();
    Show show = showRepository.findById(showId).orElseThrow();
    List<ShowSeat> showSeats = showSeatRepository.findAllById(seatIds);

    // STEP A — check
    for (ShowSeat showSeat : showSeats) {
        if (showSeat.getShowSeatStatus() != ShowSeatStatus.AVAILABLE) {
            throw new IllegalStateException("Seat unavailable");
        }
    }

    // STEP B — set
    for (ShowSeat showSeat : showSeats) {
        showSeat.setShowSeatStatus(ShowSeatStatus.BLOCKED);
    }
    showSeatRepository.saveAll(showSeats);

    // ... create and return Booking
}

Looking closely at STEP A and STEP B: these are two separate steps, not one single atomic action. If Thread A and Thread B both run this method at almost the same time, tracing exactly what goes wrong:

Both threads can finish STEP A before either one reaches STEP B.
Both see the seat as AVAILABLE, because nothing has changed yet.
Both then go ahead and mark the seat BLOCKED in STEP B.
Both go on to create a Booking, so one physical seat gets sold twice.

This gap, checking something, then acting on it, with no protection in between, is called a check-then-act race condition. It is the exact same shape of bug already seen once before in this course, in Parking Lot's Gate.assignSpot() "two gates, one spot" problem, just with a seat and a payment window in place of a gate and a ticket. The fix works the same way too: don't let the check and the write happen with nothing protecting the gap between them.

Hidden Pitfalls
Treating "check availability, then update status" as a single atomic step: these are always two separate database operations under the hood; without explicit protection, another thread can slip into the gap between them, exactly as demonstrated above.
Assuming this bug only theoretically matters and won't show up in practice: this is precisely the kind of bug that looks fine in casual, single-user testing and only surfaces under real concurrent load, which is exactly why Section 6 builds a real multi-threaded test to prove the fix rather than trusting it on inspection alone.
Section 5: Solving It, Soft Locking, and Why the Easy Fix Fails
5.1 The Tempting but Wrong Fix

The obvious fix: wrap the entire flow, selection, confirmation, and payment, inside one single database transaction, holding a lock the whole time, only releasing it once payment finishes or the user gives up. Considering the practical problem with this directly: payment can take minutes, entering card details, OTPs, slow banks. Holding a transaction open that entire time keeps a real database connection and a row lock busy for no good reason.

Option 1 — long-held transaction:
~5 min average hold per attempt.
Every minute: a real connection + row lock, sitting idle.
At scale: this kills database performance.
VERDICT: correct in theory, unusable in practice.

5.2 The Real Fix, Soft Locking
SOFT LOCK: not a database lock at all.
Our own STATUS FIELD (ShowSeatStatus) acts as the lock.
"Locked" simply means status = BLOCKED —
no database resource is actually being held.

The transaction protecting the check-then-set moment is now milliseconds long, not minutes. Once the status becomes BLOCKED, the transaction ends immediately. The 15-minute hold itself is handled separately, using blockedAt and a background check, not by keeping a transaction open the whole time.

Advantages:
1. No long-running transaction
2. Saves CPU, memory, and database connections
3. The "lock" is just data — anyone can read and understand it

5.3 Does a Short Transaction Alone Fix the Race?

Making the transaction short does not automatically make it safe. A question worth checking carefully: Spring's default isolation level, READ_COMMITTED, only guarantees that unsaved data is never read. Running this session's short check-then-set code at this default level, does the race condition actually go away?

Tracing it out with real timestamps:

Isolation: READ_COMMITTED (Spring default)

T=0ms  Thread A starts its transaction.
T=1ms  Thread A reads ShowSeat A1: AVAILABLE.
T=2ms  Thread B starts its transaction.
T=3ms  Thread B reads ShowSeat A1: AVAILABLE.
       (Nothing has been saved yet, so READ_COMMITTED sees no issue.)
T=4ms  Thread A sets status = BLOCKED and commits.
T=5ms  Thread B — still going by its T=3ms read (AVAILABLE) —
       also sets status = BLOCKED and commits.

RESULT: Both succeed. Both create a Booking. One seat, sold twice.

READ_COMMITTED only protects against reading unsaved data.
It does NOT check "did someone else change this row
between my read and my write?" That's exactly our gap.

A short transaction alone did not save this. An isolation level that actually catches this kind of conflict is needed instead:

@Transactional(isolation = Isolation.SERIALIZABLE)
public Booking bookMovie(Long userId, List<Long> seatIds, Long showId) {
    ...
}

Before tracing this, it helps to understand the actual test the database runs. SERIALIZABLE does not check anything mysterious, it asks one simple question:

"If I had run these two transactions one at a time, in some order, could I have ended up with what's happening right now?"

Testing both possible orders by hand, before looking at the real concurrent trace:

IMAGINE: A runs completely first, then B runs completely.

1. A checks seat A1 → AVAILABLE. A sets it to BLOCKED. Done.
2. B starts. B checks seat A1 → it's now BLOCKED (A already changed it).
3. B's own check fails: "seat unavailable." B never gets to book it.

RESULT of this order: only A succeeds.

IMAGINE: B runs completely first, then A runs completely.

1. B checks seat A1 → AVAILABLE. B sets it to BLOCKED. Done.
2. A starts. A checks seat A1 → it's now BLOCKED (B already changed it).
3. A's own check fails: "seat unavailable." A never gets to book it.

RESULT of this order: only B succeeds.

In neither hypothetical order does both A and B succeed. No matter which one runs "first," the second one always sees a BLOCKED seat and gets rejected by the normal availability check. This is exactly the rule SERIALIZABLE enforces: since there is no possible one-at-a-time order where both A and B succeed, the database will never allow both to succeed when they actually run at the same time either. Real concurrent execution must match one of these valid "one-at-a-time" stories, and in every valid story here, exactly one person wins.

Watching this actually get enforced, step by step, in real time:

Isolation: SERIALIZABLE

T=0ms  Thread A starts its transaction.
T=1ms  Thread A reads ShowSeat A1: AVAILABLE.
T=2ms  Thread B starts its transaction.
T=3ms  Thread B reads ShowSeat A1: AVAILABLE.

       (So far: both A and B are carrying around the belief
        "seat A1 is AVAILABLE" — but only ONE of them can
        actually be right by the time they try to act on it.)

T=4ms  Thread A writes status = BLOCKED, and commits.
       → A1 is now BLOCKED for real, in the database.

T=5ms  Thread B now tries to write status = BLOCKED too —
       but B is still acting on its belief from T=3ms,
       which said AVAILABLE. That belief is now WRONG,
       because A changed the row in the meantime.

       → The database notices: "B read this row earlier, and
         since then, someone else (A) has already committed a
         change to it. If I let B's write through, that matches
         NEITHER of the two valid one-at-a-time orders we just
         worked out — it would create a THIRD, impossible outcome
         where both A and B succeeded."

       → So the database refuses. Thread B's transaction is
         aborted with a serialization failure (in Spring, this
         usually surfaces as CannotAcquireLockException).

RESULT: Only Thread A's booking succeeds. Thread B fails cleanly
        — not because of a bug, but because the database enforced
        the same rule worked out by hand above.

In plain terms: the database is refusing to let reality do something that could not have happened if these two transactions had run one after another. That is the entire idea behind SERIALIZABLE, nothing more mysterious than that.

A check worth confirming directly: in the two "imagine running one at a time" scenarios above, did the identity of who commits first (A or B) ever change the fact that exactly one of them wins? No. No matter which one goes first, the second one always fails its own availability check. Only which one wins changes; that only one wins never changes. This is exactly why, in a real concurrent run, it's fine if the winner flips between runs, sometimes A, sometimes B, but it must never be both, and must never be neither.

One last practical note: the application code's job is simply to catch this failure and turn it into a clean message, such as "sorry, that seat was just taken, please choose again," instead of letting it crash the request outright.

5.4 Why synchronized Alone Wouldn't Work

A reasonable-sounding idea: skip isolation levels entirely and just wrap the method in Java's synchronized keyword, guaranteeing only one thread runs it at a time. Checking whether this would actually work for BookMyShow: synchronized only coordinates threads inside the same JVM, the same running server process. BookMyShow, at real scale, runs on many servers behind a load balancer.

        Load Balancer
        /          \
Server 1 (JVM #1)  Server 2 (JVM #2)
lock: L1           lock: L2
   |                   |
User A               User B
synchronized(L1)     synchronized(L2)
   ↓                   ↓
      Same MySQL database, same ShowSeat row

synchronized on Server 1 only blocks other threads on Server 1. It has no effect at all on Server 2, a completely separate process with its own separate lock that knows nothing about Server 1's lock. Both servers can still race straight into the exact bug already found earlier. The protection needs to live where the shared data actually lives, the database, not inside any one server's memory. SERIALIZABLE works because it isn't a Java lock tied to one server, it's enforced by the database itself, which every server genuinely shares.

Considering a hypothetical: suppose BookMyShow only ever ran on ONE server, forever, no scaling, no second instance. Would synchronized be a fine fix then? It would at least be correct, one JVM, one lock, no race between A and B on the same seat. But it would still be a bad fix, for a completely different reason:

synchronized on the whole method:
  → blocks EVERY booking attempt, globally.
  → seat A1, seat B7, a totally different show — ALL of it
    waits in line, one at a time, even though most of these
    don't conflict with each other at all.

SERIALIZABLE:
  → only blocks threads that are ACTUALLY touching the same row.
  → unrelated bookings still run fully in parallel.

Even on a single server, synchronized would needlessly force the entire booking system through one single queue, seat A1 and seat B7, booked by two completely unrelated users, would wait behind each other for no reason at all. SERIALIZABLE gives the same correctness, but only pays the cost where a real conflict actually exists.

Quiz Recap

Thread A books seat A1 for the 7 PM show. At the same time, Thread B books a completely different seat, B7, also for the 7 PM show. Both run inside @Transactional(isolation = Isolation.SERIALIZABLE). What happens?

A) Both fail, SERIALIZABLE means only one transaction can run anywhere in the system at a time
B) Both succeed independently, SERIALIZABLE only blocks conflicts on the SAME rows; A1 and B7 don't overlap at all
C) Only Thread A succeeds, because it appears first in the code
D) Both succeed, but the second one to commit quietly overwrites the first one's seat list
Correct answer: B. A common mistake is thinking "serializable" means "only one thing runs at a time," but it does not. It only guarantees consistency when transactions actually touch the same data. A1 and B7 are different rows, so both can run and commit fully in parallel, exactly the advantage synchronized could never provide, even on a single server.
Why A is wrong: it invents a global, system-wide lock that SERIALIZABLE does not actually impose; the guarantee is scoped to conflicting data, not to the entire system.
Why C is wrong: code order has no bearing on which transaction commits first in a genuinely concurrent execution; there is no rule favoring code that appears earlier in a file.
Why D is wrong: it describes silent overwriting, which is exactly the failure mode SERIALIZABLE is designed to prevent, not something it permits.
Hidden Pitfalls
Assuming a shorter transaction is automatically a safe transaction: reducing a transaction's duration reduces the window for a race condition but does not close the check-then-act gap itself; READ_COMMITTED at any duration still allows two threads to both read the same stale "AVAILABLE" value.
Believing SERIALIZABLE blocks all concurrent execution system-wide: it only blocks conflicting access to the same data; unrelated rows continue to process fully in parallel, as demonstrated by the A1/B7 quiz.
Reaching for synchronized as a "simpler" fix without considering server topology: synchronized only coordinates threads within a single JVM; any system running on more than one server instance has no protection at all against the exact race condition it was meant to prevent.
Assuming synchronized would at least be a good enough fix on a single server: even then, it forces every booking attempt through one single queue regardless of whether the requests actually conflict, unnecessarily serializing unrelated work that SERIALIZABLE allows to run in parallel.
Section 6: Proving It, a Real Concurrency Test
What It Means

Just as with Parking Lot, this fix is not taken on faith, it gets proven with real threads.

Practical Mechanics
public class ConcurrencyTest {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService executor = Executors.newFixedThreadPool(2);
        Long showId = 1L;
        List<Long> seatIds = List.of(101L, 102L); // SAME seats, both threads

        Runnable userA = () -> {
            try {
                Booking booking = bookingService.bookMovie(1L, seatIds, showId);
                System.out.println("User A booked: bookingId=" + booking.getId());
            } catch (Exception e) {
                System.out.println("User A failed: " + e.getMessage());
            }
        };

        Runnable userB = () -> {
            try {
                Booking booking = bookingService.bookMovie(2L, seatIds, showId);
                System.out.println("User B booked: bookingId=" + booking.getId());
            } catch (Exception e) {
                System.out.println("User B failed: " + e.getMessage());
            }
        };

        executor.submit(userA);
        executor.submit(userB);
        executor.shutdown();
        executor.awaitTermination(10, TimeUnit.SECONDS);
    }
}

These are two genuinely separate Runnables, run on two separate threads, targeting the exact same seat IDs, and this matters a great deal. Calling bookMovie() twice from the same thread, one after another, would never actually trigger this bug, the test would pass without proving anything real. This is the exact same trap already called out once, in the Parking Lot concurrency test.

Expected output, one run:

User A booked: bookingId=501
User B failed: could not execute statement; SQL... serialization failure

Running it again, the winner might flip, maybe B succeeds and A fails this time. That is completely fine and expected, deciding who commits first is a genuine race. What should never happen, on any run, is both printing "booked" for the same seats.

A question worth answering directly: if this test ran 100 times in a loop, what's the one thing that should be checked every single time? Exactly one of the two always succeeds, and exactly one always fails, never zero successes, and never both succeeding. This is the real proof, not "it worked once," but "it's impossible for both to succeed," demonstrated across many runs.

Hidden Pitfalls
Calling the method twice from the same thread instead of from two separate threads: this never actually creates the interleaving needed to trigger the bug, producing a test that passes without proving anything about real concurrent behavior.
Treating a single successful test run as sufficient proof: since which thread wins is genuinely random, one run only shows one possible outcome; the real proof requires repeated runs confirming the invariant (exactly one success, never zero, never two) holds every time.
Section 7: Building BookingService
What It Means

Turning the plan into real, working code:

public class BookingService {
    public Booking bookMovie(Long userId, List<Long> seatIds, Long showId) {
        // 1. Get user  2. Get show
        // ---- LOCK ----
        // 3. Get ShowSeats  4. Check available  5. Throw if not
        // 6. Mark BLOCKED  7. Save
        // ---- END LOCK ----
        // 8. Create Booking  9. Return
    }
}

Checking directly whether this is soft locking, based on everything reasoned through in Section 5: yes, the "lock" here is just the ShowSeatStatus field changing, not a long-running transaction.

A naming note worth flagging: the plan above says "mark as LOCKED." The actual enum from Post-Read 9 has no LOCKED value, it has BLOCKED, which already means exactly this, a seat held during payment, from R10. The existing value is used rather than inventing a new one that means the same thing.

R10 also specified a maximum of 10 seats per booking. Nothing enforces that yet, so it gets added first.

Practical Mechanics
@Service
public class BookingService {
    private static final int MAX_SEATS_PER_BOOKING = 10; // R10

    private BookingRepository bookingRepository;
    private ShowRepository showRepository;
    private ShowSeatRepository showSeatRepository;
    private UserRepository userRepository;
    private PriceCalculator priceCalculator;

    @Autowired
    public BookingService(BookingRepository bookingRepository,
                           ShowRepository showRepository,
                           ShowSeatRepository showSeatRepository,
                           UserRepository userRepository,
                           PriceCalculator priceCalculator) {
        this.bookingRepository = bookingRepository;
        this.showRepository = showRepository;
        this.showSeatRepository = showSeatRepository;
        this.userRepository = userRepository;
        this.priceCalculator = priceCalculator;
    }

    @Transactional(isolation = Isolation.SERIALIZABLE)
    public Booking bookMovie(Long userId, List<Long> seatIds, Long showId) {

        // R10 — hard cap on seats per booking
        if (seatIds.size() > MAX_SEATS_PER_BOOKING) {
            throw new IllegalArgumentException(
                "Cannot book more than " + MAX_SEATS_PER_BOOKING + " seats in one booking");
        }

        // 1 & 2 — fetch user and show
        User user = userRepository.findById(userId)
                .orElseThrow(() -> new NoSuchElementException("User not found: " + userId));
        Show show = showRepository.findById(showId)
                .orElseThrow(() -> new NoSuchElementException("Show not found: " + showId));

        // 3 — fetch the ShowSeats
        List<ShowSeat> showSeats = showSeatRepository.findAllById(seatIds);

        // 4 & 5 — check availability (this + SERIALIZABLE is our real protection)
        for (ShowSeat showSeat : showSeats) {
            if (showSeat.getShowSeatStatus() != ShowSeatStatus.AVAILABLE) {
                throw new IllegalStateException(
                    "Seat " + showSeat.getSeat().getNum() + " is no longer available");
            }
        }

        // 6 & 7 — soft-lock: flip status, save immediately
        for (ShowSeat showSeat : showSeats) {
            showSeat.setShowSeatStatus(ShowSeatStatus.BLOCKED);
            showSeat.setBlockedAt(new Date());
        }
        showSeatRepository.saveAll(showSeats);

        // Price — R12, handled by PriceCalculator (Section 9)
        int amount = priceCalculator.calculatePrice(show, showSeats);

        // 8 — create the booking, PENDING (payment not done yet)
        Booking booking = new Booking();
        booking.setUser(user);
        booking.setShow(show);
        booking.setShowSeats(showSeats);
        booking.setAmount(amount);
        booking.setBookingStatus(BookingStatus.PENDING);
        booking.setBookedAt(new Date());

        // 9 — save and return
        return bookingRepository.save(booking);
    }
}

An honest note on scope: BookingStatus.PENDING stays as-is for now, actually charging money and moving to CONFIRMED is a separate flow, not built today. The same applies to the 15-minute expiry, nothing yet automatically moves an unpaid BLOCKED seat back to available. Both are named clearly and left as homework.

Hidden Pitfalls
Enforcing R10's seat cap after the database calls instead of before: checking seatIds.size() > MAX_SEATS_PER_BOOKING should happen as the very first check, before any repository calls, so an invalid request fails fast without wasting a database round trip.

Applying the Checklist to Both Responses

Point 1, matches our contract?

BookingService calls int amount = priceCalculator.calculatePrice(show, showSeats);. Neither AI version actually fits that call: neither takes (show, showSeats), both only take showSeats, missing the Show parameter entirely. Response #2 also returns double, not int, assigning that straight into int amount = ... would not even compile without an explicit cast, not a style nitpick, a genuine contract break. Two different bugs, same category: AI wrote a method signature it invented on its own, not the one this actual codebase needs. The lesson worth keeping: always check the exact call site before trusting AI's method signature.

Point 2, follows our style?

Mostly fine in both, @Component, clean methods throughout. Response #2's stream-based style is somewhat more modern than what has been used elsewhere in this codebase, worth a note, but not a blocker on its own.

Point 3, handles edge cases?

Comparing how the two responses treat an unrecognized or missing seat type: Response #1 silently falls into default: total += 150 for anything that isn't "GOLD"/"SILVER", no warning, just a guessed price. Response #2 actually does better here, explicitly guarding against null seats and empty lists before doing anything else, a genuinely good habit AI added on its own this time. A useful reminder here: AI mistakes aren't always uniformly "AI is bad," one version can be better in one specific way and worse in another; each piece deserves its own judgment.

Point 4, fits OUR real requirement (R12)?

This is the decisive one. R12, from Post-Read 8, established that price depends on the Show plus the SeatType, not the seat type alone, exactly why ShowSeatType exists as its own class, keyed on both. Response #1 hardcodes flat prices tied to specific string names ("GOLD", "SILVER"), a matinee GOLD seat and a night-show GOLD seat cost the same, and it breaks silently for any theatre using different names. Response #2 makes an even more fundamental mistake: it treats SeatType as if it were a fixed Java enum (VIP, PREMIUM, EXECUTIVE, NORMAL), with a switch over fixed cases. But SeatType was deliberately built as its own real entity, back in Post-Read 9, specifically because different theatre chains define their own seat-tier names, and a fixed enum cannot hold two different theatres' value sets at once. AI's second response directly contradicts a design decision made on purpose. Neither version touches Show or ShowSeatType at all, both ignore that price is supposed to depend on which specific show a seat belongs to.

Regardless of which exact version came back, the same real gap shows up: AI has no way of knowing about ShowSeatType, since that is a decision unique to this system, not something a generic prompt reveals. This is why point 4 is always the one that matters most, the other three are checkable by reading the code alone; this one requires actually knowing the system's own design.

Practical Mechanics: The Correct Fix

The fix is the same regardless of which AI response was the starting point, using the real relationship already established in this system:

public interface ShowSeatTypeRepository extends JpaRepository<ShowSeatType, Long> {
    Optional<ShowSeatType> findByShowAndSeatType(Show show, SeatType seatType);
}

@Component
public class PriceCalculator {

    private ShowSeatTypeRepository showSeatTypeRepository;

    @Autowired
    public PriceCalculator(ShowSeatTypeRepository showSeatTypeRepository) {
        this.showSeatTypeRepository = showSeatTypeRepository;
    }

    public int calculatePrice(Show show, List<ShowSeat> showSeats) {
        int total = 0;
        for (ShowSeat showSeat : showSeats) {
            SeatType seatType = showSeat.getSeat().getSeatType();
            ShowSeatType showSeatType = showSeatTypeRepository
                    .findByShowAndSeatType(show, seatType)
                    .orElseThrow(() -> new NoSuchElementException(
                        "No price configured for seatType " + seatType.getName()
                        + " on show " + show.getId()));
            total += showSeatType.getPrice();
        }
        return total;
    }
}

A matinee Show and a night Show, on the same screen and same SeatType, now correctly get two separate ShowSeatType rows, and two separate prices. No hardcoding, no assumptions about seat-type names, and no confusion between SeatType as an entity versus as an enum.

Common Pitfalls Summary
1. Assuming Hibernate automatically escapes reserved SQL keywords.
   -> It does not; a class name colliding with a reserved word
      (like "user" or "show") requires an explicit
      @Entity(name = "...") to avoid breaking table creation.

2. Fixing a reserved-keyword conflict only for the currently-used
   database.
   -> Leaves a landmine for any future switch to a different
      database engine with a different set of reserved words.

3. Using plain @Controller for a JSON API endpoint.
   -> Spring treats the return value as a view name to render,
      not as data; @RestController (or @ResponseBody) is required.

4. Passing full model objects across the Controller boundary
   instead of DTOs built from IDs.
   -> Exposes internal structure and creates unnecessary coupling
      between this system's internal shape and every API consumer.

5. Treating "check availability, then update status" as one
   atomic step.
   -> These are always two separate database operations; without
      protection, another thread can slip into the gap between
      them (a check-then-act race condition).

6. Assuming a shorter transaction is automatically a safe
   transaction.
   -> READ_COMMITTED at any duration still allows two threads to
      both read the same stale value before either writes.

7. Believing SERIALIZABLE blocks all concurrent execution
   system-wide.
   -> It only blocks conflicting access to the same data;
      unrelated rows (like two different seats) still run fully
      in parallel.

8. Reaching for Java's synchronized keyword as a fix for a
   multi-server system.
   -> synchronized only coordinates threads within a single JVM;
      a system running on more than one server has zero
      protection against the exact race it was meant to prevent.

9. Assuming synchronized would at least be a good fix on a
   single server.
   -> Even then, it forces every request through one queue
      regardless of whether requests actually conflict,
      needlessly serializing unrelated work.

10. Calling a concurrency-sensitive method twice from the same
    thread instead of from two real, separate threads in a test.
    -> Never actually creates the interleaving needed to trigger
       the bug; the test passes without proving anything.

11. Treating a single successful concurrency test run as
    sufficient proof.
    -> Which thread wins is genuinely random; real proof requires
       repeated runs confirming the invariant holds every time.

12. Trusting a single AI-generated method signature without
    checking it against the actual call site.
    -> AI frequently invents its own signature rather than
       matching what the existing codebase actually calls.

13. Hardcoding seat-type prices as string literals or fixed enum
    cases inside pricing logic.
    -> Directly contradicts R12 and the SeatType-as-entity design
       decision; price must be looked up through ShowSeatType.

Assuming AI's mistakes are consistent enough to memorize a single "gotcha" going forward: this session's own two real AI responses made genuinely different mistakes on the same prompt; relying purely on the four-point checklist, rather than memorizing any one specific failure pattern, is what actually generalizes across different runs and tools.

Key Terminology
Term	Meaning in Simple Words
@Entity(name = "...")	An attribute on @Entity that sets the actual database table name explicitly, used to avoid conflicts when a class name collides with a database's reserved keyword (such as user or show).
@RestController	A Spring annotation combining @Controller and @ResponseBody, telling Spring to send a method's return value back as raw data (typically JSON) rather than treating it as the name of a page to render.
Check-Then-Act Race Condition	A race condition arising specifically from checking a condition (such as "is this seat available") and then acting on that check (marking it unavailable) as two separate, non-atomic steps, allowing another thread to act in the gap between them.
Soft Locking	A locking strategy that uses an ordinary data field (such as a status column) to represent a "locked" state, rather than holding an actual database lock or transaction open for an extended period.
Isolation.SERIALIZABLE	The strictest standard database transaction isolation level, which guarantees that the result of running transactions concurrently must match some valid outcome of running those same transactions one at a time, in some order; violations cause one transaction to fail with a serialization error.
Serialization Failure	The error a database raises when it detects that allowing a transaction's write to proceed would produce a result impossible under any valid one-at-a-time ordering of the concurrent transactions involved.
@Autowired (constructor)	A Spring annotation marking a constructor for automatic dependency injection; optional when a class has exactly one constructor, but required once a class has more than one.

Frequently Asked Interview Questions

1. Why can a class named Show cause a real database failure even when its Java code is completely correct?
Every database engine reserves a specific set of keywords for its own internal commands. If Hibernate uses a class's plain name to generate its table name, and that name happens to match one of those reserved words (as SHOW does in MySQL), the resulting CREATE TABLE statement conflicts with the database's own syntax. This is entirely independent of whether the Java code itself is correct; the fix, @Entity(name = "shows"), explicitly overrides the generated table name to sidestep the conflict.

2. What is the practical difference between @Controller and @RestController, and why does an API endpoint need the latter?
@Controller is designed for returning view names that Spring resolves into rendered HTML pages. @RestController is @Controller combined with @ResponseBody, which instructs Spring to serialize the method's return value directly as the response body (typically JSON) instead of treating it as a page name. Any endpoint intended to serve an API client, rather than render a browser page, needs @RestController to correctly return structured data.

3. Precisely describe the check-then-act race condition in the naive bookMovie() implementation, and explain why it is a genuine bug rather than a rare edge case.
The naive implementation performs two separate operations: first, checking whether every requested ShowSeat has status AVAILABLE (Step A), and second, updating each one to BLOCKED (Step B). Because these are two distinct database interactions rather than one atomic operation, two threads can both complete Step A, both observing AVAILABLE, before either one reaches Step B. Both then proceed to mark their seats BLOCKED and create a booking, resulting in the same physical seat being sold to two different users. This is not a rare edge case; it is a predictable, reproducible outcome any time two requests for the same seat arrive close enough together in time, which becomes increasingly likely as the volume of concurrent requests to a popular show grows.

4. Why does holding a database transaction open for the entire selection-confirmation-payment flow fail as a solution, even though it would technically prevent the race condition?
Payment can take anywhere from seconds to several minutes, involving card entry, OTP verification, and third-party bank processing delays outside the application's control. Holding a database transaction, and the row lock and connection that come with it, open for that entire duration means a real, scarce database resource sits idle for the length of an unpredictable external process. At any meaningful scale, this exhausts available database connections and severely degrades performance, making the approach correct in principle but unusable in practice.

5. Explain soft locking, and identify precisely what does and does not get held for an extended period of time under this approach.
Soft locking uses an ordinary data field, ShowSeatStatus, as the mechanism representing a "locked" seat, rather than an actual database lock. The transaction that checks availability and flips a seat's status to BLOCKED completes in milliseconds and ends immediately afterward; no database lock or connection is held during the (potentially minutes-long) payment process that follows. The temporary hold itself is represented purely as data (the BLOCKED status plus a blockedAt timestamp), checked and expired later by separate logic, rather than by any database resource being held open.

6. Trace through why READ_COMMITTED, Spring's default isolation level, fails to prevent the race condition even when the transaction protecting the check-then-set logic is short.
READ_COMMITTED only guarantees that a transaction never reads data that another transaction has started but not yet committed. It does not detect or prevent the scenario where two transactions both read the same committed value (AVAILABLE) before either one writes a change, then both proceed to write based on that now-stale read. In the traced timeline, Thread A and Thread B both read AVAILABLE at T=1ms and T=3ms respectively, and Thread A's commit at T=4ms has no effect on Thread B's decision, since Thread B is still acting on its earlier read; both successfully mark the seat BLOCKED, reproducing the exact race condition the isolation level was hoped to prevent.

7. Explain, in terms of "valid one-at-a-time orderings," precisely what guarantee Isolation.SERIALIZABLE provides.
SERIALIZABLE guarantees that the outcome of running transactions concurrently must match some outcome that could have resulted from running those same transactions completely sequentially, one at a time, in some order. Working through both possible sequential orderings of Thread A and Thread B booking the same seat shows that in either order, only one of the two ever succeeds, the second one always finds the seat already BLOCKED and fails its own availability check. Since no valid sequential ordering produces "both succeed," SERIALIZABLE guarantees the database will never permit both to succeed when they actually execute concurrently either; if a conflicting write is detected, one transaction is aborted with a serialization failure.

8. Why does Java's synchronized keyword fail to protect against this race condition in a real, multi-server deployment of BookMyShow?
synchronized only coordinates threads running within the same Java Virtual Machine process. In a real deployment behind a load balancer, distinct server instances run as entirely separate JVM processes, each with its own independent lock object. A synchronized block on Server 1 has no visibility into, or effect on, threads running on Server 2, even though both servers are reading and writing the exact same rows in the same shared MySQL database. Two requests landing on different servers can still race straight into the original bug, since the protection lives in server memory rather than in the shared database itself.

9. Even in a hypothetical single-server deployment where synchronized would technically be correct, why would it still be a poor design choice compared to SERIALIZABLE?
synchronized applied to the entire booking method would serialize every booking attempt across the whole system, forcing unrelated requests, for entirely different seats, on entirely different shows, to queue behind one another even though they share no actual conflicting data. SERIALIZABLE only blocks transactions that are actually contending for the same row; two threads booking genuinely different seats proceed and commit fully in parallel. synchronized would be correct but needlessly costly in throughput; SERIALIZABLE provides the same correctness while only paying the cost where a real conflict exists.

10. Why must a concurrency test for this bug use two genuinely separate threads, and what specifically would be wrong with calling bookMovie() twice sequentially from one thread instead?
A race condition, by definition, depends on two operations interleaving in time in a way that a single sequential thread of execution can never produce. Calling bookMovie() twice in a row from the same thread means the first call fully completes, including its transaction commit, before the second call even begins; there is no possibility of both calls reading the seat as AVAILABLE simultaneously. Only two independent threads, executing concurrently and both attempting to act on the same data at nearly the same moment, can actually recreate the interleaving that exposes this specific bug.

11. According to R12 and the SeatType/ShowSeatType design established in this course, why is it fundamentally incorrect for PriceCalculator to determine price from SeatType alone, regardless of how that lookup is implemented?
R12 explicitly states that price is a function of the Show and the SeatType together, not the seat type in isolation, which is precisely why ShowSeatType, keyed on both Show and SeatType, exists as its own dedicated entity. Any implementation that determines price purely from a seat's SeatType (whether through hardcoded string matching or a fixed enum switch statement) cannot represent the fact that the same seat type may legitimately carry different prices across different shows, such as a matinee versus a night show, or a weekday versus a weekend show on the same screen. The only correct approach queries ShowSeatType using both the specific Show and the specific SeatType together.

12. Explain why the two real AI responses shown for PriceCalculator, despite being genuinely different from each other, both failed the same fourth checklist point.
Response #1 hardcoded prices tied to specific string seat-type names, and Response #2 treated SeatType as a fixed Java enum with hardcoded cases; these are different implementations making different specific mistakes. However, both share the same underlying failure: neither response has any way of knowing that this particular system deliberately built ShowSeatType as a dedicated pricing entity keyed on both Show and SeatType, since that is a decision unique to this system's own design history, not something a generic prompt about "calculating price by seat type" could reveal. This is precisely why checklist point 4, fitting the system's own real, specific design, catches issues the other three points cannot; it requires knowledge of this system specifically, not just general code-quality judgment.

## 4. Redesign data migration plan (`redesign-data-migration-plan.md`, 2026-08-23)

**Decision rule:** change how the curriculum is *discovered and read*, don't discard what was entered. Treat current PostgreSQL data as source material: additive schema → backfill links → verify pages against real data → archive obsolete seed-only records.
**Preserve:** every `StudyVertical`/`StudyTask` + completion flags + module labels; Java courses/modules/lessons/resources/problems/comparisons/diagrams/notes; Atlas domains/concepts/prereqs/relations; `ConceptNextLesson` text until linked by `LessonId`; user-entered Reading Map rows. **Code debt (not DB):** old charts/radar/AI-insight copy/unused dashboard components.
**Replace/archive only after backfill:** duplicate/placeholder Reading Map titles; list-like titles ("Structured concurrency (8)") → computed counts; 8 manual activity counts → computed from real events; raw arrow paths → normalized steps; text-only next-lesson rows → `LessonId` links. Before any archive: backup, export rows, record IDs, use `ArchivedAt`/`IsSeeded` marker first.
**Additive schema:** `course_domain_links`, `lesson_concept_links (RelationshipType)`, `study_task_lesson_links` (became `study_task_content_links`), linked Reading Map fields (`LessonId`, `StudyTaskId`, `Status` Planned|Reading|Completed|Revisited|Deferred|Archived, `ScheduledFor`, `Priority`, `IsSeeded`, `ArchivedAt`), `learning_activity` events, `knowledge_thread_steps`; plus compatibility columns (`Verticals.canonical_vertical_id/archived_at`, `courses.path_type` Course|Certification|Project, `lessons.content_status`).
**Curriculum mapping:** FDE Curriculum/Self-Study → FDE path(s) after row-level reconciliation; Java & Spring vertical → Java path linked to Foundations/Backend/Reliability domains; Azure → Cloud/Agentic-AI certification path; Lab Projects → dedicated Projects path (not Reading Map); Atlas → links to courses/lessons (no React constants).
**API corrections:** `POST /api/chapters/map` saved none of prerequisites/related/next, matched courses by loose title, and **silently fell back to `java-spring-lld` or the first course**; must resolve stable slugs, require explicit destination, never create/choose implicitly, persist relations, return canonical URL, validate unknown names; remove the frontend's optimistic "mapped in session buffer" success fallback. Composed reads: `/api/learning-paths[/{slug}]`, Atlas with destinations, Reading Map with computed activity, chapter with links. Readiness must fail on migration failure (startup previously swallowed it).
**App changes:** Home/Atlas data-driven; nav exposes Atlas, Reading Map, Library, Java/FDE/Azure/Projects with legacy vertical URLs as compatibility links; `/reading-map` → ReadingMap (not aliased to LabProjects); distinct Lab Projects page; importer loads valid paths and shows saved canonical URL; ChapterReader uses configured API base + auth headers with explicit unavailable state; keep legacy detail routes until crosswalk accepted.
**Safe order:** protect/inspect → add links → correct writes → expose content → replace prototypes → retire only after acceptance. **AWS acceptance checklist:** valid TLS; no migration/missing-table errors in logs; Atlas/reading-map/chapter responses contain DB data not fallback samples; each vertical discoverable; test import lands only in selected path with relations; completion consistent across path and Reading Map.

## 5. Technical migration architecture (`technical-migration-architecture.md`, HEAD `a0d02fc`, impl baseline `7102e4d`)
- **"Semantically large but physically small":** 15–22 engineer-days for the safe connection MVP, 24–40 for full migration (5–8 calendar weeks solo, 3–5 with two engineers; +20% if prod DB differs from seed model); authoring the FDE's 104 outline bodies is a separate editorial effort.
- Old frontend is not scraped/embedded; both apps use the .NET API + same PostgreSQL during transition. Canonical model = `Course→CourseModule→Lesson/Problem`; legacy `StudyVertical→StudyTask` stays as compatibility until every old item has a verified destination. No destructive change in the first migration.
- **Canonical ownership:** lesson completion = `Lesson.IsCompleted` (linked `StudyTask.IsCompleted` mirrors transactionally); practice = `Problem.IsCompleted`; unmapped tasks stay task-owned; Atlas placement via course-domain/lesson-concept links; reading queue linked `ReadingMapItem`; activity from `learning_activity`; **v2 uses explicit `completed:true|false`, not toggle** (retries can double-invert); old toggle endpoints become adapters.
- **Release sequence (all additive):** 1 `HardenMigrationExecution` → 2 `AddCurriculumBridgeSchema` → 3 `AddLinkedReadingAndActivity` → 4 `NormalizeKnowledgeThreads` → 5 `AddMigrationReconciliation` → 6 content backfill command v1 (Java exact, FDE/Azure/Lab outlines, Atlas links) → 7 `TightenVerifiedMappingConstraints` → 8 cleanup release much later. **Never put environment-specific matching in an EF `Up()`**; migrations create schema, a versioned reconciliation command does discovery/backfill and writes audit rows.
- **Invariants:** legacy task/completed-task/notes/problems counts unchanged; every verified bridge row has exactly one canonical target; unique `(module_id, slug)`; no archived legacy row physically deleted; no page reports sample data as DB data. For duplicate FDE rows report raw and deduplicated counts labelled.
- **Risk register highlights:** prod schema differs from migrations (High/High → restore rehearsal, fail-fast migrator); FDE verticals not true duplicates; old/new progress divergence; importer writes wrong course; static fallback hides API failure; browser API key permits writes; empty outline lessons look complete (→ `ContentStatus`); mutable `latest` image obscures rollback (→ digests).
- **First slice:** harden migration + readiness; add the three link tables; map Java's 17 lessons + 5 OOP problems; `ProgressService` + explicit v2 endpoints; `/api/v2/learning-paths/java-spring-lld`; React `/learning-paths/java-spring-lld`; verify old `/vertical/5` and new path both show 8/22.

## 8. Future platform (AWS) migration plan (`future-platform-migration-plan.md`, 2026-08-24)
**Target:** Git push → validate/test → one immutable multi-platform image release (digests + SBOM) → verified backup → one-shot migrate/seed → deploy → health/smoke → keep previous release for rollback. **Later platform:** Route 53/HTTPS → CloudFront + S3 (React) → ALB → **ECS Fargate** API with autoscaling → **RDS PostgreSQL** in private subnets; GitHub Actions + OIDC → ECR → ECS; Terraform/OpenTofu; **EKS only if justified**. Non-goals now: Kubernetes, microservice split, auto-applying reconciliation each deploy, destructive cleanup, **rewriting into a different backend stack** (that is a separate decision — `08-…`), treating a frontend-embedded API key as auth.
Baseline findings (Aug 24): compose pulls GHCR `latest` by default; API `--migrate`, `--seed-reference-data`, `--reconcile-content --scope --dry-run|--apply|--verify` lifecycle contract; `deploy-api.yml` (then) built arm64 only, tagged SHA+`latest` but pulled `latest`, didn't wait for SSM completion, didn't run migrate/seed, stopped containers before proving replacements healthy, pruned all images (weakening rollback). Backup scripts `scripts/backup-db.sh`/`restore-db.sh` (pg_dump custom → S3; record source DB identity, SHA, checksum; rehearse restore in an isolated DB; verify the `/dev/null` redirect spelling in restore's container detection).
Stages: **0** single-EC2 automation (digest-pinned deploy, poll SSM to completion, backup → pull → `--migrate` → `--seed-reference-data` → optional reconcile dry-run → start replacements → wait `/health/ready` → smoke → remove old after bake; idempotent bootstrap — never `down -v`, never overwrite env file) · **portable images** (`linux/amd64,linux/arm64` index, `imagetools inspect` release check, not `amd64/v4`; fixes the AMD64-host-can't-pull-ARM64-only failure) · **1** IaC for the existing shape (VPC, SGs, instance profile, SSM, DNS/cert refs, backup bucket, host bootstrap; encrypted versioned remote state) · **2** Postgres → RDS (encrypted, PITR, deletion protection, SG only from app; freeze writes → verified dump → restore into new DB → count/checksum compare → switch secret → migrate/seed → keep EC2 DB read-only for rollback window) · **3** ECS Fargate + ALB (desired count 1, then 2; migration/seed tasks before service update; circuit breaker; log retention; mind RDS connection limits) · **4** S3 + CloudFront (OAC, hashed immutable assets, short-cache `index.html`, no privileged secret in JS). Minimum-preserve list: verticals/tasks, canonical courses/modules/lessons, notes/resources/diagrams/authored content, completion flags/timestamps, reconciliation/link rows, user/profile IDs and activity. Milestones M0–M7 (inventory → reliable single-EC2 → portable images → reproducible EC2 → RDS cutover → ECS+ALB → S3/CloudFront → operational maturity). Cost controls: keep single EC2 until repeatability/availability is a real problem, one small RDS, Fargate count 1, avoid NAT gateways, S3/CloudFront, log retention, Budgets/anomaly alarms, tags `project/environment/owner/cost-center/managed-by`.
**What actually happened since:** Stage 0 was largely implemented Aug–Sep (SSM deploy, digests, S3 backups, arm64 verification, S3 deploy-log capture — see `04-…`). RDS/ECS/CloudFront were **not** started; prod is still one arm64 EC2 host.
